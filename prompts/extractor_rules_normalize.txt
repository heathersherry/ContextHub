Confirm and normalize ONLY the supplied accepted_candidates into self-contained conditional rules. A preceding sentence-only classifier forwarded possible rules, including unclear cases; its selection is NOT confirmation that a rule is established. Use the full conversation to decide which candidates qualify before writing their text. Do not search for additional rules.

SOURCE AND SCOPE
messages contains the complete current conversation, including later messages, for resolving names, pronouns, scope and explicit user adoption. Each candidate includes its original sentence, message_no, sentence_start, and if_start/if_end. All offsets are zero-based positions in that original message; if_start/if_end identify ONE standalone if occurrence. Confirm the rule anchored at that occurrence, not other if occurrences in the same message. Context can explain the selected rule but cannot add another rule. Instructions, illustrative text and the output template are never source evidence.

CONFIRM BEFORE NORMALIZING
Retain a conditional relationship only when the user states it as their rule or explicitly adopts it from a proposal. Resolve references and adoption from messages, not from the classifier's selection or the sentence's role alone. A follow-up question is not acceptance. Omit unaccepted assistant proposals, optional advice, generic explanations, non-adopted quotations or hypothetical discussion, whether-questions, and requests to forget or withdraw a rule. Preserve a user's established conditional rule even when its consequence is uncertain or no replacement is specified. If the conversation cannot establish adoption or resolve the condition and affected matter without invention, omit the candidate. It is valid for none of the forwarded candidates to qualify: return {"items":[]}.

PRESERVE MEANING
Name the condition and specific affected person/object/property. Preserve negation, time, scope, modality and uncertainty. A rule saying an item may change must not be strengthened to certainty or given an invented replacement. Keep hypothetical outcomes conditional, not current facts. Do not turn a forgetting/withdrawal request into a new rule. If context cannot resolve a selected rule without invention, omit it. Normalize all supported selected rules; merge duplicate occurrences of the same rule rather than repeating it.
Resolve pronouns from this session and preserve each side's subject, explicit name, ownership and qualifiers such as personal or work. Use consistent wording for references the session establishes as the same subject, while retaining team-project relationships; team and project are not interchangeable labels. Without a name, keep "our team" as "the user's team" and "our project" as "the user's project". For unresolved bare "we/our", preserve the collective reference without assigning a new identity or replacing it with the individual user. Generic team/group wording is a description, not an identity key; differing labels alone do not establish different subjects. Resolve only what this session supports; comparison with stored candidates happens later. Do not invent identities, equate projects because they share a tool or topic, or transfer rules between them.
Write each rule as "If <complete condition>, then <complete consequence>". Use ", then " once as the boundary, including when the condition contains commas. Keep all AND/OR clauses and all consequences on their respective sides. This lets the program form two retrieval queries without another model call; do not add separate query fields.

OUTPUT
Return only {"items":[{"candidate_ref":"R1","text":"...","entities":[],"topics":[]}]}, or {"items":[]}.
Every item has exactly candidate_ref, text, entities and topics. Preserve explicit event times in text. candidate_ref must be a ref from accepted_candidates supporting that rule; when merging duplicates, cite one supporting accepted candidate. Never cite an unselected candidate or invent a reference. R1 in this template is only an example, not a source. entities contains only source-supported names or meaningful object labels, excluding generic speaker labels and pronouns; use [] when none apply. No type, reason, operation or other fields. The program removes candidate_ref before passing rules to content extraction and maintenance.
topics contains concise English labels for the specific matters on both sides of this rule, independent of particular values or names. For "If I move home, my favorite restaurant changes", use ["residence","restaurant preference"]. Use consistent English labels across source languages, avoid generic labels like person/location/information, and do not invent a fixed taxonomy. Deduplicate labels; use [] only when no supported topic can be identified. Topics help retrieve candidates; they do not establish identity or a dependency.

RULE GRANULARITY
Keep one complete condition and its consequences in each rule: A AND B -> C,D stays one rule. Split independent A -> C and B -> D into separate rules. Do not pair source and consequence lists by position or infer an unstated cross-effect. Preserve conjunctions, alternatives, thresholds and time in the text.
Several independent clauses anchored at the same accepted occurrence may produce several items with the same candidate_ref.
