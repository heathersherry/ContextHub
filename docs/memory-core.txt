ContextHub managed memory
=========================

Purpose
-------
Applications and MEME both use contexthub.memory for fact/rule extraction, update
and forgetting decisions, condition binding, invalidation, repair, retrieval, and
context assembly. The benchmark adapter handles data conversion, official answer
templates, scoring, and experiment reports. The core does not read task types,
gold answers, or benchmark graph labels.
The shared-core refactor did not integrate MemDerive or alter maintenance prompts.
See memory-research/memory-core-pl001-20261026.txt for its pl_001 live-model
experiment and pre-commit regression results. That experiment predates the joint
extraction change described in memory-research/joint-extraction-20261026.txt.

Extraction confirms candidate rules, extracts independent content and identifies
actual forgetting requests in one full-session LLM request. Case-insensitive
standalone if and remove/forget/delete hints form separate candidate groups.
Rule hints exclude recognized code regions: Markdown fences and inline code,
HTML pre/code elements, bare Python conditional lines and braced if lines.
The filter preserves original source offsets and the full conversation. Prose
explaining code remains eligible for semantic screening; syntax alone does not
decide whether it establishes a user rule. Forgetting hints are unchanged.
Optional Jev screening uses one request with separate three-way questions:
rule/not_rule/unclear and forget/not_forget/unclear. Each policy and its detailed
criteria appear once in shared state. Positive and unclear candidates survive.
Numeric source offsets stay in audit logs; multi-if sentences use <target> tags.
The extractor receives selected source sentences under accepted_candidates.rules
and accepted_candidates.forget_requests. It confirms only candidates in the
corresponding group; full messages provide adoption, reference and scope context,
not additional rule or forgetting candidates. Jev-rejected sentences stay excluded,
including when another sentence in the same message survives. Without Jev, all
program candidates enter these groups. An empty group forbids output items of
that type, enforced by the parser; forgetting requests without a screening keyword
are not discovered by the joint extractor.

The model returns one items array with type=rule/content/forget_request, directly
in source conversation order. The parser validates the whole array atomically and
preserves its order; there is no numeric order field, regrouping or rules-first
pass. Only content has temporal_scope. Forgetting requests are recorded in session
output, never inserted as facts.

With p2_direct_backend=jev, explicit verbatim memory requests are routed to inform
by the program: an imperative Remember/Please remember this/these/the following
header, followed by word for word/verbatim and a colon with supplied content.
Only the header is matched; quoted payload words do not determine the route.
Bare remember mentions, questions, negations and other forms stay with Jev.
The remaining contents receive inform/correction/hold classifications in one
batch with shared instructions and criteria. Original C positions are preserved.
Program decisions are logged as p2_intent.program, separate from Jev answers.
Rules and forget_requests are excluded; no remaining questions means no Jev call.
This shortcut only selects inform; normal new/update/duplicate/history maintenance
still applies. It does not bypass old-memory checks or guarantee verbatim storage. Actual
maintenance remains sequential, so later operations see earlier accepted writes.
The inform intent means providing information, not necessarily creating a record.
Its p2_inform prompt selects new/update/duplicate/history against old facts.
Duplicate ignores the incoming item: no memory/version write, source merge,
accepted result or new protection. The existing record remains unchanged and
can still be checked by downstream conditions.
Direct maintenance no longer accepts invalidate: an ended state is saved with
update as an explicit, supported negative fact in the same matter. The old version
remains potentially true history. Coexisting hobbies/subscriptions do not replace
one another without evidence; extra records may be updated to ended states only
when the statement establishes the same superseded state. Conditional and
basis-reference invalidation still propagate downstream changes.
Forgetting bypasses content classification, retrieves old disclosures at execution
time, confirms deletion scope, and marks selected matters and all versions deleted.
It reuses the prepared query embedding without a redundant generic candidate search.
The shared-activity deletion policy (including the James cooking example) remains
in p2_forget_scope.txt. See memory-research/forget-batch-flow-20261026.txt for
implementation details and validation limits.

P1 checks an existing rule only against newly accepted, unlinked fact matters
whose retrieval pool contained that rule. Known condition/affected endpoints are
removed before candidate filtering and are not rejudged. New or revised rule
versions still receive initial binding using their retrieval hits, accepted
session facts and prior-version endpoints. Selected new links are appended; old
links are not automatically reviewed or removed. Empty pools make no model call.

Application entry points
------------------------
The existing ContextHub HTTP server exposes:
  POST /api/v1/memories/ingest
  POST /api/v1/memories/context
Python SDK methods: client.memory.ingest(request), client.memory.context(request).
See examples/memory_application.py for a complete example.

Ingestion requests contain namespace, a consecutive sequence starting at 1,
messages, and an optional timestamp. Each message contains role, content, and an
optional timestamp. A namespace identifies an application's conversation or
project space. Account and agent identities come from the existing request headers
and authentication flow via the server's RequestContext, not the request body.
Reads and writes within the same account, identity, and namespace are serialized;
concurrent operations return 409 memory_namespace_busy. Separate scopes operate
independently. The SDK does not automatically retry ingestion; model request
retries are recorded through the core's shared call ledger.
Calls can take a long time. The example explicitly sets client timeout=1800;
configure proxy timeouts accordingly.

Context requests contain namespace and query, with optional mode and max_chars:
  auto: Route by question text, without reading benchmark labels.
  answer: Valid current facts.
  policy: Valid facts, with conditional rules listed separately.
  history: Usable historical facts; deleted or explicitly invalidated statements
           are excluded from evidence.
The context field can be passed directly to the application's answering model.
The items field includes memory version references, types, statuses, derivation
bases, and source_sessions. Provenance currently identifies input batches, not
individual message event IDs.
max_chars limits only the context string and preserves complete entries rather
than cutting facts or rules. It excludes metadata such as items and is not a token
budget. budget_exhausted indicates whether the budget excluded any material.
Queries make embedding requests; the core does not generate the application's
final answer.

Deployment
----------
After installing the server and SDK, configure the existing server environment:
  MEMORY_ENABLED=true
  MEMORY_CONFIG_PATH=/absolute/path/to/memory-config.json
  MEMORY_CHAT_API_KEY=...
  MEMORY_EMBEDDING_API_KEY=...
Start with examples/memory-config.json, adjust model names, endpoints, and request
parameters for your providers, and set a suitable response_archive_directory.
The example contains no credentials.

The server entry point remains contexthub.main:app. Managed memory uses the existing
DATABASE_URL, with tables in the contexthub_memory schema. It does not reuse or
overwrite public.contexts or public.execution_attempts.
Set initialize=true for the first installation; the database role must be able to
create the schema and pgvector extension. Set it to false after initialization if
desired. Existing schemas are checked for matching embedding models, dimensions,
prefixes, and full-text search configuration.

The default flow uses an LLM. To use the existing Jev experiment paths, set
candidate_gate_backend, p1_backend, and p2_direct_backend to jev as needed, and explicitly
provide jev_retry and TYPESAFE_API_KEY. p1_jev_threshold is configurable.
Applications and MEME share component implementations but can use different model
parameters; sharing the core does not imply identical scores across configurations.

Interface changes
-----------------
The old /api/v1/knowledge/* endpoints, client.knowledge, and
KNOWLEDGE_ENABLED/KNOWLEDGE_CONFIG_PATH settings have been removed from the public
interface. Replace the settings with MEMORY_* above. MemoryService's former
automatic maintenance path using injected discovery, detection, and extractor
components has also been removed, without a compatibility layer.
Historical experiments still use internal knowledge research components, so those
components have not been deleted wholesale. Examples and tests for the old public
interface have been replaced with SDK-to-HTTP-to-core-to-database coverage.

client.memory.add/list/promote still store, list, and share manually supplied
content using the existing permissions flow. Memories managed through ingest live
in the core's versioned tables and should be read through context. They are not
copied into ctx:// documents or integrated with existing team sharing, unified
search/assemble, or lifecycle deletion. These are the current interface boundaries;
memory.list does not enumerate all managed memories.

Failure boundaries
------------------
Maintenance performs multiple persistent writes and does not guarantee atomic
rollback of an entire batch. If a model call or process fails midway, the core
blocks reads of incomplete state and ingestion of the next batch, returning
memory_ingestion_incomplete. Applications can retain original inputs and replay
them in order into a new namespace. Automatic checkpoint recovery is not implemented.
A complete result means processing finished. Facts may remain stale if a rule
cannot be confirmed or repair cannot complete; context selection excludes unusable
current facts. The existing algorithm is retained and does not guarantee correct
model decisions in every case.

MEME and existing data
----------------------
integrations/memebench/memory_research retains the dataset, official answer template,
and scoring logic. run_id/episode_id/strategy_id map to tenant_id/namespace/owner_id
only at the adapter boundary. Experiment results retain episode_id and run_id;
raw database exports use the core's generic column names.
Core prompts ship in src/contexthub/memory/prompts; answer and scoring prompts live
in integrations/memebench/memory_research/prompts. Each run freezes both sets
separately, without changing a global prompt path between runs.

New databases can still be initialized with scripts.memory_research.init_db.
For an existing research database, stop all clients, back it up, and explicitly run:
  MEMORY_DATABASE_URL=... python -m contexthub.memory.migrate_research
The migration moves tables and renames scope fields in one transaction, preserving
memory IDs, versions, provenance, configuration, and original call records.
The new core does not silently create an empty store alongside an old schema.
This command was validated only on temporary databases, not run against the user's
experiment databases. Historical outputs and frozen source snapshots are unchanged.
Old programs should no longer connect to a migrated database.
